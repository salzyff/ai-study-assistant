# Study AI security update

## Before deploying
1. In Supabase SQL Editor, run `server/supabase/migrations/005_session_security.sql`. Run it before deploying the backend. It creates a private session registry, checks revoked sessions and bans, and restricts existing study tables to the Express service role. It does not delete study data. Existing older logins must sign in again. If it fails, stop and resolve the SQL error before deployment.
2. In Supabase Authentication email-provider settings, enable Confirm email, Secure password change and Secure email change. Set minimum password length back to 6 if you previously raised it to 12. Enable password-change notification emails if available. Keep your functioning Brevo SMTP configuration.
3. In Supabase URL Configuration, set your exact production Site URL and allow that URL as a redirect for recovery; avoid broad production wildcard redirects. The password reset email template must include `{{ .ConfirmationURL }}`.
4. Deploy the frontend from `studyassist` and the backend from `server`. Keep the secret Supabase key on the backend only. Existing .env files are preserved in this download; UPDATE_GITHUB.ps1 excludes them.
5. Sign in fresh, then complete the checks below.

## What changed
- Profile password change sends an email link before showing the reset form. New/reset passwords have a 6-character form minimum. Successful password reset requests global sign-out, requiring devices to sign in again.
- Every protected Express request validates the token with Supabase, checks its session ID against auth.sessions and checks the user's ban status, then checks a private, database-backed inactivity timer. Revoked or expired sessions are rejected even if their JWT has not expired.
- Sessions expire after one hour without authenticated API activity. While the app is visible and online, it sends a heartbeat every 30 seconds; closing it, leaving it hidden or going offline stops those heartbeats. Other in-flight API requests can update last activity. Another visible tab sharing that session keeps it active. This is time away, not a fixed hourly logout while studying.
- Expiry is sticky per login session. Token refresh and reloading cannot revive it. A new sign-in is required. Database failure fails closed with a temporary-unavailable response.
- Offline open screens lock after an hour without a successful heartbeat (or on wake if the browser suspended timers). Sign-out clears displayed conversations and administrator state.
- Study tables no longer allow direct anonymous/authenticated Supabase REST access, which would bypass Express security checks. Existing frontend study requests all use Express.
- Protected responses use no-store. Request IDs are generated by the server, and request logs omit query strings.
- Vercel headers prevent framing, block object embeds, restrict base URL changes, disable unused device permissions, and disable content sniffing. This is a partial CSP, not a full script allowlist.

## Limits you should understand
Supabase Secure Password Change can exempt recently signed-in sessions from reauthentication. The Study AI screen always uses an email link, but this does not force email verification on every direct call to Supabase's own password-update API. Do not describe this as universal email enforcement. Strict universal enforcement would require a different provider policy or a separately designed authentication layer.
The one-hour rule protects this application's Express API and UI; it does not change Supabase Auth's own refresh lifetime. Database grants close the study-data bypass. Review any additional tables/views/RPCs you create later before exposing them to clients.
This is targeted hardening, not a penetration test or a guarantee that the entire app has no vulnerabilities. SMTP delivery, hosted database behavior and actual browser sessions still need the deployment checks below.

## Checks after deployment
- Register: mismatched passwords and passwords shorter than 6 are rejected; email confirmation still arrives.
- Profile > Change password: no immediate password-edit form; email arrives, its link opens reset, password change succeeds, and old sessions cannot access study data. Old password fails.
- Use two accounts: one cannot open the other's conversations/tasks; a normal member cannot open admin routes. Original environment admin protection stays in place.
- Suspend a test member: their existing session is denied on its next API request. Restore the member and sign in again.
- Leave all tabs hidden/closed for over an hour, then reopen. A fresh sign-in is required. Staying visibly online keeps the session active.
- For a quicker session-expiry check using a TEST account only, find its row in app_sessions and move last_seen back by 61 minutes in SQL Editor. The next heartbeat must sign it out. Never alter auth.sessions timestamps. Sign in again afterwards.
- Sign out and replay the old token only against your own test account: protected routes should return 401.
- SQL Editor: confirm app_sessions has RLS enabled and only service_role can execute check_app_session. Anonymous/authenticated users must have no access to the listed study tables.
